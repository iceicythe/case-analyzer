版本依据：2026-10-17 工作目录与最近验证记录。完整解释见 [项目复盘](PROJECT_REVIEW.md)；50 个问题和演示安排见 [面试准备](INTERVIEW_PREP.md)。

## 1. 开场只记这一段

> 这是一个智驾测试日志分析工作台，用规则筛选减速候选，用受约束的大模型做事件复核和人工分流，确认后整理多模块证据、选择排查检查项，支持记录、离线报告和飞书提醒。我重点关注的是证据约束、失败恢复和评测口径。当前功能流程已验证，真实业务提效与 AI 相对规则的收益还需要独立数据对照。

## 2. 六句话不能混

| 术语 | 一句话解释 |
|---|---|
| 候选 | 宽松筛出的值得查看区域 |
| 参考区间 | 程序按严格规则算出的区间 |
| AI 确认 | 模型结论通过程序门槛，与严格参考一致 |
| 人工标签 | 人按口径核查保存；独立评测标签不能直接拿 AI 结果代替 |
| 检查建议 | 下一步看什么证据、怎么核对、缺什么 |
| 根因结论 | 需要更完整证据和验证，当前工具不自动保证 |

## 3. 记牢数字，知道它们从哪来

| 项目 | 当前值 | 含义 |
|---|---|---|
| 采样 | 0.1 秒 | 当前车辆事件协议的网格 |
| 窗口 | 0.5 秒 | 6 个点、5 个间隔，不是 5 个点 |
| 宽松候选 | 降速≥0.6 m/s，下降间隔≥3，回升≤0.2 m/s | 保留待复核区域 |
| 严格事件 | 降速≥1.0 m/s，下降间隔≥4，回升≤0.1 m/s | 符合项目事件定义 |
| 单间隔下降 | ≥0.01 m/s | 计入下降间隔 |
| 桥接间隔 | ≤0.5 秒 | 还需完整采样、无回升、端点下降等条件 |
| 数值容差 | 1e-6 | 避免浮点误差改变边界 |
| 相关模块对齐 | 0.15 秒容差 | 不代表已经同步时钟 |
| 候选覆盖阈值 | 0.9 | 候选并集覆盖真值的比例 |
| 事件 IoU 阈值 | 0.5 | 一对一事件匹配 |
| 单 Case 文件总计 | ≤24 MB | 导入限制 |
| 每份 CSV | ≤200000 行 | 导入限制 |
| 飞书合并 | 默认 5 秒、每条最多 20 个 Case | 进展更新，不代表全批完成 |
| 测试记录 | 最近 107 项通过 | 功能回归数量，不是业务准确率 |

## 4. 三组状态分开回答

- **模型输出状态：** validated、call_failed、needs_manual_review、stale。
- **候选业务处置：** pending_ai、ai_confirmed_event、ai_rejected_candidate、needs_human、human_reviewed。
- **后台任务状态：** queued、running、complete、failed、changed。

后台 complete 表示本轮自动步骤结束，候选仍可能需要人工；报告 model_validated 表示受约束模型输出通过校验，工程师可能尚未执行检查。

## 5. 十个最重要的追问

1. **规则都算完了还要 AI？** 当前 AI 不能独立改边界，价值是受约束复核、疑点和检查排序；需要消融证明边际收益。
2. **加速度和 TTC 怎么用？** 加速度辅助事件理解；TTC 留排查。差分加速度不是独立传感器证据。
3. **怎么限制编造？** 固定事实/区间/引用、schema const、本地业务校验；受控时间线说明；不声称消灭全部幻觉。
4. **数据途中改了？** 请求前后核对依赖指纹，不一致 stale，旧结果不可当当前结果。
5. **断了怎么恢复？** 任务落盘、有效结果检查点；未知 in-flight 请求明确重试，不能保证无重复计费。
6. **转人工算 FN 吗？** 自动确认 Recall 中有效事件未自动命中就是 FN；候选覆盖是另一项。
7. **评测怎么防污染？** 先冻结预测与资源，再回放标签、开启对照；不等于独立盲标。
8. **建议质量怎么评？** 原始事实与引用、可执行性、无无依据结论；当前事件脚本不评报告质量。
9. **飞书能恰好一次吗？** 本地去重、发送状态和 unknown；远端已收但本地没记成功时无法端到端保证。
10. **你自己做了什么？** 按实际说需求、口径、核查、能解释和修改的模块，说明 AI 辅助范围。

## 6. 三个公式与一个签名细节

```text
Precision = TP / (TP + FP)
Recall = TP / (TP + FN)
IoU = 交集时长 / 并集时长

自动处理覆盖率 = 自动确认或排除的候选数 / 全部冻结候选数
事件持续时间 = end_time - start_time

飞书签名：
key = timestamp + "\n" + signing_secret
sign = Base64(HMAC-SHA256(key, 空消息))
```

分母为零时指标未知，不自动写 0% 或 100%。事件匹配是一对一，重复预测仍会产生 FP。

## 7. 两个故事优先练

**故事 A：合法 JSON 仍在编造。** 类型和非空校验挡不住“故障已确定、延迟 999 秒”；改为同 observation 允许文本与引用绑定，并在保存重放、渲染验证。说明结构正确和语义可靠的区别。

**故事 B：函数返回仍是失败。** 旧评测把 review 返回计成成功，但返回记录可以是 call_failed；改为读保存状态、保留失败分母，报告未评就明确未评。说明执行、校验、业务、建议四层状态的区别。

任选一个再讲到修改函数、失败输入、验证测试；不要只背“做了异常处理”。

## 9. 面试前最后检查

- 不看笔记讲 90 秒介绍，能说清自己的贡献和 AI 辅助范围。
- 手算一次六点窗口、一次桥接判断、一次 IoU 与重复匹配。
- 从 `review` 追到 Prompt、validate、route、保存与指纹。
- 打开一份报告，把一条建议追到字段、时段、引用与判断分支。
- 演示一次正式保存与刷新，解释草稿、人工区间和候选关联的区别。
- 准备一个独立演示目录；不打开有密钥的配置，不用私有数据屏幕共享。
- 说清“还没有测出的收益”，并给出规则/AI 对照和计时方案。

## 10. 现场卡住时的回答方式

先说自己确定的事实，再说明边界，最后提出验证方法。例如：

> 当前用的是带容差近邻匹配，我能说明缺失和歧义怎么统计。真实执行延迟还涉及采集时钟与链路，因此我不会把这项偏差直接报成控制延迟。如果要验证，需要先核对时钟来源和同步，再用完整请求与执行反馈做对照。

这比猜一个技术名词或承诺未经验证的能力更容易继续讨论。
